## 0. 一頁摘要

- 城堡做在現有的 `hall.html`（導覽列已經有「大廳」），保留網站頁首頁尾，畫面中間放遊戲畫布。
- 使用 **Phaser 3（固定 3.90.0 版）**，把官方打包好的單一 `phaser.min.js` 檔案直接放進 repo（`assets/vendor/`），**不用 npm、不用建置步驟、不用外部 CDN**。這是新的規則例外，需管理員同意。
- **所有房間共用一個「房間場景」程式**，房間差異全部寫在「房間定義檔」（用文字畫的地圖＋演出點清單），新增房間＝新增一個定義檔。
- 角色外觀與行為分開：行為只會呼叫「轉向」「換姿勢」，畫幾何色塊或未來畫像素圖都由「外觀」模組負責。
- 演出點只寫**一套通用流程**（走過去 → 轉向 → 換姿勢 → 停留並冒泡泡 → 離開），坐椅子、彈琴、剪羊毛只是資料不同。
- 成員資料沿用現有 `data/members.json`；城堡專用的外觀與台詞放兩張新的平面資料表，**沒填外觀的成員會依 id 自動配色**，所以 80 人以上也不用一個一個填。
- 第一版只做：公會大廳＋演奏室、約 10 位 NPC、走動／碰撞／避讓、E 鍵或點擊對話、門口切換場景、兩種演出點（椅子、樂器）。

## 1. 現有網站架構分析與整合方式

### 1.1 現況

| 項目 | 現況 | 對城堡的影響 |
|---|---|---|
| 頁面 | 多頁靜態 HTML，`hall.html` 是「虛擬大廳（籌備中）」預留頁，目前只載入 `pages/static.js` | 直接把 `hall.html` 改成城堡頁，網址與導覽列不變 |
| 共用版面 | `layout.js` 產生頁首頁尾 | 城堡頁照用，遊戲只佔 `<main>` 內的一塊 |
| 資料 | `data.js` 是唯一讀資料的地方，`config.js` 設定每張表來源（試算表 CSV，失敗退回本地 JSON） | 新增兩張城堡資料表，一樣走 `loadTable()` |
| 成員 | `data/members.json` 26 位（真實暱稱），欄位：`id`(m01…)、`nickname`、`aka`、`game`、`role`… **沒有「現役／歷史」欄位** | 抽選直接讀它；現役／歷史欄位列為【未定】 |
| 驗證 | `validate.js` 驗 id、圖片網址、YouTube | 新增「顏色碼」驗證 |
| 樣式 | `tokens.css` 集中變數，`pages.css` 已有 `.hall` 區塊 | 城堡頁外框樣式寫在 `pages.css` 的 `.hall` 區塊，用 tokens 變數 |
| 規則 | 不准框架、npm、建置；相對路徑；外部資料不准進 `innerHTML` | Phaser 需新增例外（見 1.3） |
| 管理頁 | `tools/admin/` 的 Apps Script，管理試算表各分頁 | 城堡資料表第一版只用本地 JSON，管理頁支援列為【後續】 |

### 1.2 整合方式【必做】

```
hall.html                     ← 改寫：頁首頁尾＋遊戲區＋操作說明＋對話框
assets/vendor/phaser/         ← 新增：phaser.min.js（3.90.0）＋ LICENSE（MIT 授權）
assets/js/pages/hall.js       ← 新增：頁面進入點（讀資料 → 啟動遊戲）
assets/js/castle/             ← 新增：遊戲模組（見第 3 節）
data/castle_looks.json        ← 新增：成員外觀（平面）
data/castle_lines.json        ← 新增：台詞（平面）
```

- `hall.html` 先用一般 `<script src="assets/vendor/phaser/phaser.min.js">` 載入 Phaser（會產生全域變數 `Phaser`），再用 `<script type="module" src="assets/js/pages/hall.js">` 載入我們自己的程式。其他頁面完全不載入 Phaser，不影響原網站速度。
- 原本 `hall.html` 的構想說明文字縮成遊戲下方的一小段「操作方式／目前進度」。
- 讀取失敗或瀏覽器不支援時，顯示友善訊息與原本的佔位圖，不整塊空白。

## 2. 推薦技術與套件

| 選項 | 建議 | 理由 |
|---|---|---|
| 遊戲函式庫 | **Phaser 3.90.0**（單檔，放進 repo） | 內建鏡頭跟隨、鍵盤滑鼠觸控輸入、簡單物理碰撞、補間動畫、場景切換，省下自己寫的大量程式；AI 代理對 Phaser 3 的寫法很熟，出錯少 |
| 不選 Phaser 4 | 暫不採用 | 較新、網路範例與 AI 熟悉度較少，改版差異會增加除錯成本。等原型穩定後再評估【後續】 |
| 不選自己寫 Canvas | 備案 | 可以完全不違反「不用框架」，但鏡頭、輸入、碰撞、縮放都要自己寫，約多 500～800 行且較易出錯。若管理員不同意例外，就走這條 |
| 地圖格式 | **第一版：在 JS 檔裡用文字畫地圖**（`#` 牆、`.` 地板…） | 一眼看得懂、修改只改幾個字元、AI 修改時耗用的文字量很小、不用另外裝地圖編輯器 |
| 地圖格式（之後） | Tiled 地圖編輯器的 JSON【後續】 | 換像素素材時 Phaser 能直接讀；只換「畫地圖」那一層，演出點與 NPC 不用改 |
| 物理 | Phaser 內建 Arcade（只用在訪客撞牆、撞家具） | NPC 走格子路線，不需要物理 |
| 尋路 | 自己寫的格子「廣度優先搜尋」（約 40 行） | 房間最大約 40×28 格，計算量很小；不需要另裝套件 |
| 文字 | 對話框用頁面 HTML（`textContent`），名字標籤用 Phaser 文字 | 中文在放大的畫布上容易糊；HTML 對話框清楚、可被螢幕報讀，也符合安全規則 |
| 隨機 | 自己寫可指定種子的亂數（約 10 行） | 測試時用 `?seed=123` 每次抽到一樣的人、一樣的位置，方便比對畫面 |

不引入其他套件（不用尋路套件、狀態機套件、UI 套件）。

## 3. 第一版遊戲架構與主要模組【必做】

### 3.1 檔案與責任

```
assets/js/pages/hall.js        頁面進入點：讀資料、抽選、建立 Phaser 遊戲、接上 HTML 對話框
assets/js/castle/
  config.js        遊戲常數：格子大小、畫面尺寸、NPC 上限、速度
  rng.js           可指定種子的亂數、洗牌、隨機取區間
  roster.js        抽選成員、分配房間、合併外觀與台詞（純函式，不碰畫面）
  grid.js          解析文字地圖、判斷能不能走、格子尋路、格子預約（避讓用）
  rooms/
    index.js       房間清單（id → 定義），以及樓層／門的連接
    hall.js        公會大廳定義：文字地圖、家具、演出點、門、容量
    music.js       演奏室定義
  actions.js       演出動作表：sit、play、read…（姿勢、泡泡、停留秒數）
  RoomScene.js     唯一的房間場景：依房間定義畫地圖、放家具、放 NPC、處理門
  avatar.js        外觀：GeometricAvatar（幾何色塊），提供 setFacing / setPose / say
  npc.js           NPC 行為：狀態機、走路、使用演出點
  player.js        訪客：鍵盤移動、互動判定
  dialog.js        HTML 對話框（textContent 顯示、Esc 關閉）
  debug.js         除錯圖層（?debug=1）：格子、演出點、NPC 狀態
```

約 14 個小檔案，每個 50～200 行。**刻意不做**：事件匯流排、元件系統、依賴注入、通用外掛架構。

### 3.2 資料流

```
hall.js
  └ loadTable('members' / 'castle_looks' / 'castle_lines')   ← data.js
  └ roster.draw(members, looks, lines, rooms, rng)          → { roomId: [npc資料…] }
  └ new Phaser.Game({ scene: RoomScene })
        └ RoomScene.create({ roomId, spawn })
              ├ grid.parse(room.map)
              ├ 畫地板、牆、家具（幾何）
              ├ 只為這個房間的 NPC 建立 Avatar + Npc
              └ 碰到門 → 淡出 → scene.restart({ roomId: 目的地, spawn })
```

- 抽選結果在整次遊玩中保留（存在記憶體），所以切換房間再回來，還是同一批人；**重新整理頁面就重新抽選**。
- 離開的房間不繼續模擬，回來時 NPC 從隨機位置重新開始（看起來一樣自然，程式簡單很多）。

## 4. 場景管理與地圖尺寸

### 4.1 比例【必做】

| 項目 | 建議值 | 說明 |
|---|---|---|
| 格子（Tile） | **32×32 像素** | 常見像素素材尺寸，日後最容易找／畫素材 |
| 遊戲內部畫面 | **640×360**（20×11 格多一點） | 16:9，等比放大到容器寬度（Phaser `Scale.FIT`），像素不糊（`pixelArt: true`） |
| 角色站位 | 腳底對齊格子，碰撞框約 20×12（腳邊一小塊） | 可以貼著桌邊走，不會卡住 |
| 角色外觀高度 | 約 40～48 像素（頭會超出格子上緣） | 和日後 32×48 的像素角色相同，替換時位置不用重調 |
| 前後遮擋 | 依腳底 y 座標排前後（`setDepth(y)`） | 走到桌子後方會被擋住 |
| 移動速度 | 訪客約 120 像素／秒，NPC 約 50～70 | NPC 慢一點比較有生活感 |

房間比畫面小時置中顯示；比畫面大時鏡頭跟著訪客，且不超出地圖邊界。

### 4.2 房間尺寸與容量建議

依照提供的平面配置草圖（1F 大廳居中、左上酒館、右上演奏室、左下鍛造工坊、右下練習室、正門往下通外庭；2F 客房與圖書館；3F 觀星台）：

| 樓層 | 房間 | 尺寸（格） | NPC 容量 | 階段 |
|---|---|---|---|---|
| 戶外 | 城堡外庭（羊圈、紡車、工作台、農田、噴泉、水井） | 40×28 | 10 | 【後續】 |
| 1F | 公會大廳（中央紅毯、公告板、旗幟、往 2F 樓梯） | 28×18 | 8 | **【必做】** |
| 1F | 演奏室（舞台、鋼琴、譜架、觀眾椅） | 22×14 | 8 | **【必做】** |
| 1F | 交流廳／酒館（吧台、圓桌） | 24×16 | 8 | 【後續】 |
| 1F | 戰鬥練習室（稻草人、箭靶、武器架） | 22×14 | 5 | 【後續】 |
| 1F | 鍛造工坊 | 18×12 | 3 | 【後續・候選】 |
| 2F | 公會客房（走廊＋左右各 3 張床，共用） | 26×16 | 6 | 【後續】 |
| 2F | 魔法圖書館 | 20×14 | 4 | 【後續・候選】 |
| 3F | 觀星台 | 18×12 | 3 | 【後續・候選】 |
| 戶外 | 城堡花園 | 未定 | 未定 | 【後續・候選】 |

六個確定區域容量合計 45，大於 40 人上限，分配時不會塞不下。

### 4.3 場景切換【必做】

- 地圖文字中用 `D` 標門，房間定義寫「這扇門通往哪個房間、出現在哪個位置」。
- 訪客走進門的格子 → 畫面淡出 0.2 秒 → 載入新房間 → 淡入。
- 還沒做的房間的門照樣畫出來，但走過去只顯示「這裡還在整修中」，不切換。第一版大廳的酒館門、練習室門、正門、樓梯都是這種門，只有演奏室門能進。

### 4.4 房間定義範例（示意，非最終）

## 5. 成員與城堡資料結構

### 5.1 用 JSON，不用 JSONL【建議定案】

現有 `data.js` 與試算表 CSV 都是「一張表＝物件陣列」。改用 JSONL 要多寫一套讀取方式，又無法直接對應試算表。所以沿用 JSON 陣列、平面欄位，日後加一個試算表分頁就能接上。

### 5.2 成員：沿用 `data/members.json`

城堡只讀 `id`、`nickname`、`role`、`game`。不另外複製一份成員名單，避免兩邊不同步。

現役／歷史狀態：建議日後在 `members` 加 `status` 欄位（`active`／`former`），但會動到試算表與管理頁，列為【未定】。**第一版城堡不需要這個欄位**（所有人機率相同）。

### 5.3 新表 `data/castle_looks.json`（成員外觀）【必做】

一位成員最多一列；**沒有列的成員依 id 自動產生顏色**（同一個 id 永遠得到同一組顏色）。

| 欄位 | 內容 | 例 |
|---|---|---|
| `member_id` | 對應 `members.id` | `m01` |
| `hair` | 髮色，`#rrggbb` | `#5b3a29` |
| `outfit` | 衣服顏色 | `#3d5a99` |
| `skin` | 膚色（選填，空白用預設） | `#f1d3b3` |
| `accent` | 配件顏色（選填） | `#c9a227` |
| `mark` | 配件：`none`／`hat`／`ribbon`／`glasses`／`cape`（選填） | `ribbon` |
| `favorite` | 偏好動作（選填，第一版不用，預留給演出排程） | `play_violin` |
| `is_demo` | 示範資料 | `false` |

顏色一律經 `validate.js` 新增的 `isColor()` 驗證，不合格就用自動配色。

### 5.4 新表 `data/castle_lines.json`（台詞）【必做】

| 欄位 | 內容 |
|---|---|
| `id` | 台詞 id |
| `member_id` | 空白＝通用台詞，任何人都可能說 |
| `room` | 空白＝任何房間；填 `music` 表示只在演奏室說 |
| `text` | 一句話，純文字 |
| `is_demo` | 示範資料 |

- 互動時：先取「本人＋本房間」與「本人＋任何房間」的台詞；不夠再補通用台詞；隨機抽 1～3 句依序顯示。
- **內容規則**：個人台詞只能放成員本人提供或同意的內容，不可替真實成員編造「他說過的話」。第一版只放少量**通用、明顯是 NPC 日常的句子**（例如「今天的練習好累。」），並標 `is_demo: true`，對話框顯示「示範資料」小字。
- 日後可考慮把現有 `quotes.json`（語錄，有 `speaker`）接進來【後續】。

### 5.5 設定與載入

`config.js` 新增兩項（第一版只讀本地檔）：

```js
castle_looks: { source: 'json', url: 'data/castle_looks.json' },
castle_lines: { source: 'json', url: 'data/castle_lines.json' },
```

`FIELD_TYPES` 補上 `is_demo: 'boolean'`。日後改成試算表分頁時，只改成 `{ ...SHEET, url: '', fallback: ... }`。

## 6. NPC 隨機抽選與房間分配【必做】

1. 讀入全部成員（80 人也只是幾 KB，一次讀完沒問題）。
2. 用亂數洗牌，取前 `min(40, 成員數)` 人（第一版設定上限改為 10，方便測試）。
3. 只考慮「已開放」的房間，依容量依序分配：
   - 先讓每個房間至少分到 1 人（有人數時）；
   - 剩下的人依各房間剩餘容量的比例隨機分配，滿了就換下一間。
4. 每位 NPC 固定在被分到的房間，不跨房間。
5. 只在進入某房間時才建立那個房間的角色物件。
6. 網址參數：`?seed=123` 固定抽選結果；`?debug=1` 開啟除錯圖層。一般訪客看不到這些。

【後續】依 `favorite` 或角色職位提高進某房間的機率（例如愛拉小提琴的人較常出現在演奏室）。

## 7. 幾何角色渲染與未來 Sprite 替換

### 7.1 外觀介面（行為只認這幾個方法）【必做】

```
createAvatar(scene, look) → avatar
avatar.setPosition(x, y)
avatar.setFacing('up' | 'down' | 'left' | 'right')
avatar.setPose('idle' | 'walk' | 'sit' | 'play' | 'work' | 'read' | 'sleep' | 'cheer')
avatar.say('♪')          // 頭上小泡泡（符號或極短字），幾秒後消失
avatar.setNameVisible(true/false)
avatar.destroy()
```

### 7.2 幾何版 GeometricAvatar【必做】

- 組成：影子（橢圓）＋身體（圓角矩形，衣服色）＋頭（圓，膚色）＋頭髮（半圓，髮色）＋配件（小三角帽、蝴蝶結點、眼鏡線）。
- 面向：用兩個眼睛小點的位置表示（朝上時不畫眼睛）。
- 姿勢都用簡單位移或補間動畫：
  - `walk`：身體上下輕晃；`sit`：整體下移 6 像素、身體變矮；`play`：左右小幅搖擺＋泡泡 ♪；
  - `work`：手（小矩形）上下揮動；`read`：身前出現小書本色塊；`sleep`：躺平旋轉 90 度＋泡泡 Zz；`cheer`：小跳一下。
- 名字標籤：預設只在訪客靠近或滑鼠移過時顯示，避免 40 個名字擠滿畫面。

### 7.3 換成像素素材【後續】

- 新增 `SpriteAvatar`，實作同一組方法：`setFacing` 換方向、`setPose` 播對應動畫。NPC 行為、演出點、資料都不用改。
- 素材規格先定好：一格 32×48、腳底在下方中央、4 個方向、每個姿勢 2～4 張。
- 分層換裝（髮型、衣服、配件各一層疊起來）時，`castle_looks` 的 `hair`／`outfit`／`mark` 可改存「素材編號」或繼續當「染色」用。
- 素材必須是自製或可商用授權（例如 CC0）的原創素材，**不可使用遊戲官方圖片**。

## 8. NPC 狀態機與演出點設計

### 8.1 狀態機【必做】

```
        ┌──────────── 完成 ─────────────┐
        ▼                               │
     [idle 待機] ──隨機──▶ [wander 走動] ─┤
        │                               │
        └──隨機──▶ [goto 走向演出點] ──▶ [perform 演出] ──▶ [leave 起身] ─┘

     任何狀態 ──訪客互動──▶ [talk 面向訪客、停下] ──對話結束──▶ 回到原狀態
```

- 每次回到 `idle` 時抽下一個動作：待機 2～5 秒（40%）、走到附近隨機格子（35%）、使用一個空的演出點（25%）。比例寫在 `castle/config.js`。
- 不需要 AI 語言模型控制。

### 8.2 走路與避讓【必做】

- 只在「能走的格子」上走，路線用格子尋路算出來，所以**不會穿牆或穿家具**。
- 每位 NPC 「預約」自己下一步要踩的格子；別人已預約就停 0.5 秒再試，試 3 次還不行就重新找路或放棄這次動作。這是最簡單、也最不會卡死的避讓方式。
- 訪客不參與預約；NPC 擋路時，訪客會被它的碰撞框擋住（訪客可以繞過）。NPC 下一步若是訪客站的格子也會等待。

### 8.3 演出點：一套通用流程【必做】

所有生活動作共用同一個流程，差別只在 `actions.js` 的一筆資料：

```
1. 預約演出點（一個點同時只給一人）
2. 走到演出點格子
3. 轉向 facing
4. setPose(action.pose)，依 action.bubbles 每隔幾秒冒泡泡
5. 停留 action.duration 秒（範圍內隨機）
6. 恢復 idle 姿勢，釋放演出點
```

```js
// assets/js/castle/actions.js（示意）
export const ACTIONS = {
  sit_rest:    { pose: 'sit',  bubbles: ['…'],      duration: [8, 15] },
  sit_watch:   { pose: 'sit',  bubbles: ['👏', '♪'], duration: [10, 20] },
  play_piano:  { pose: 'play', bubbles: ['♪', '♫'],  duration: [12, 25] },
  play_violin: { pose: 'play', bubbles: ['♪', '♬'],  duration: [12, 25] },
  read_notice: { pose: 'idle', bubbles: ['？', '！'], duration: [4, 8] },
  // 後續：shear_sheep、spin_wool、hammer、hit_dummy、shoot_arrow、sleep_bed…
};
```

新增「剪羊毛」＝在 `actions.js` 加一行＋在外庭房間定義加一個演出點，不需要新程式。

第一版必做兩種：**椅子（`sit_rest`／`sit_watch`）** 與 **樂器（`play_piano`／`play_violin`）**；大廳公告板 `read_notice` 順手加入。

### 8.4 多人演出【後續】

用「群組演出點」：一個群組有多個位置（例如指揮＋三位演奏者，或兩人對坐聊天）。

1. 排程每隔一段時間檢查有沒有群組能湊齊人（房間內有足夠的 idle NPC）。
2. 一次預約群組所有位置，各自走過去。
3. 全部到齊（或等超過 15 秒就取消）後同時開始，依序冒對話泡泡。
4. 結束一起釋放。

流程與單人演出點相同，只多了「等到齊」一步，所以第一版的程式結構可以直接延伸。

### 8.5 物件互動【必做（簡單版）】

房間定義裡的物件可以有 `text`（例如公告板、旗幟），訪客靠近按 E 顯示一段固定文字。公告板內容日後可接 `site.json` 或歷史資料【後續】。

## 9. 訪客操作與互動

### 9.1 電腦版【必做】

| 操作 | 功能 |
|---|---|
| WASD／方向鍵 | 移動（斜向可走，速度一致） |
| E 或空白鍵 | 與最近的 NPC 或物件互動（距離約 1.5 格內；最近的目標頭上出現小提示） |
| 滑鼠點 NPC | 若在 3 格內直接對話；太遠顯示「走近一點再聊吧」 |
| Esc | 關閉對話框 |
| 走進門 | 切換場景 |

- 對話框是遊戲下方的 HTML 區塊：顯示名字（與職位），台詞一句一句出現，按 E／點擊看下一句。
- **鍵盤焦點**：只有在遊戲區被點擊或取得焦點時才攔截方向鍵與空白鍵，避免整個網頁無法捲動。遊戲區旁提示「點一下遊戲畫面開始操作」。

### 9.2 手機版【後續，第一版只確保畫面縮放正常】

- 畫面左下虛擬方向盤（HTML 按鈕或簡單觸控區），右下「互動」按鈕；或「點地板就走過去」（已有尋路，可重用）。
- 直式手機畫面寬度小，遊戲區維持 16:9 置頂，對話框放在下方。

## 11. 測試與驗收標準

依 `CLAUDE.md`，**不建立測試框架或 CI**。驗證方式比照 `spec.md` 第七節，在工作階段中手動執行。

### 11.1 自動檢查（每次 PR 都跑）

1. Python 檢查 `castle_looks.json`、`castle_lines.json`：能解析、平面欄位、`member_id` 對得到成員、顏色格式正確。
2. Python 檢查每個房間定義（或在除錯模式由瀏覽器檢查）：地圖每列等寬、門與演出點都在能走的格子上、每個演出點都走得到。
3. `curl` 確認 `hall.html`、Phaser 檔、所有 JS／JSON 回傳 200。
4. `grep` 確認沒有以 `/` 開頭的路徑、外部資料沒有進 `innerHTML`。
5. Playwright 開啟 `hall.html?seed=1&debug=1`：主控台無錯誤；讀取遊戲公開的狀態（`window.__castle`，只在 debug 模式提供）確認 NPC 數量正確、沒有 NPC 站在牆或家具上；模擬按鍵走進演奏室門後房間 id 改變。

固定種子＋讀狀態代替逐張看截圖，可以大幅減少視覺測試的往返次數；需要人看的只剩最後一兩張截圖。

## 13. 主要技術風險與簡化建議

| 風險 | 影響 | 簡化／對策 |
|---|---|---|
| Phaser 違反現行「不用框架」規則 | 需改規則 | 本機單檔、固定版本、只在城堡頁載入；不同意就改走原生 Canvas 備案 |
| NPC 互相卡住、走位不自然 | 視覺除錯耗時 | 格子尋路＋格子預約＋等待逾時放棄；不做連續物理避讓 |
| 反覆截圖比對很花時間與 Token | 開發成本高 | 固定種子、debug 圖層、`window.__castle` 狀態檢查，以程式判斷取代肉眼 |
| 每個演出寫成特例程式 | 難維護 | 一套通用演出流程＋動作資料表 |
| 每個房間寫一個場景程式 | 重複程式 | 唯一 `RoomScene`＋房間定義檔 |
| 中文字在放大的畫布上模糊 | 不好讀 | 對話用 HTML；名字標籤只在靠近時出現，必要時提高文字解析度 |
| 方向鍵攔截導致網頁不能捲動 | 使用者困擾 | 只在遊戲取得焦點時攔截 |
| 替真實成員編造台詞 | 違反內容規則 | 個人台詞只收本人提供；通用台詞標示示範 |
| 素材或音樂侵權 | 法律風險 | 只用自製或 CC0 素材，不用官方素材 |
| 範圍越做越大 | 第一版拖延 | 嚴守第 10 節；新想法先記在第 12 節 |
| Phaser 檔案約 1 MB（壓縮傳輸約 300 多 KB） | 城堡頁首次載入稍慢 | 只有城堡頁載入；瀏覽器會快取；顯示「載入中」 |
| 文字地圖之後要換成 Tiled | 一次性改寫 | 地圖只影響「畫地圖」與「能不能走」兩件事，演出點座標沿用格子座標 |

## 15. 第一版原型實作紀錄

- 遊戲程式：`assets/js/castle/`（約 1,500 行，含註解）＋ `assets/js/pages/hall.js`；Phaser 3.90.0 從 npm 官方套件庫取得並核對檢查碼後放進 `assets/vendor/phaser/`。
- 資料：`data/castle_looks.json`（6 位成員的示範外觀，其餘自動配色）、`data/castle_lines.json`（通用、房間專用與少量個人示範台詞，全部 `is_demo: true`）。
- 網址參數：`?seed=數字` 固定抽選、`?npcs=數字` 指定人數（上限為各房間容量合計 16）、`?debug=1` 顯示除錯圖層並提供 `window.__castle` 狀態。
- 與規劃不同的地方：
  - 畫面掉格時 Phaser 預設會把時間「抹平」，角色會變慢；已改成依真實經過時間計算（`fps.smoothStep: false`）。
  - 「點地板走過去」提前在第一版完成，手機也能用手指點地板移動、點成員聊天。
- 已知限制：沒有聲音；家具只是色塊與文字標籤；離開房間後那個房間的 NPC 不會繼續活動（回來時重新開始）；手機畫面較小，字會比較小。
